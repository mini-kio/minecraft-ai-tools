# Portable map files in a native test world

`prepareMapStage(sourcePath, { version, dimension, bounds, workDir, signal })`
returns a JSON-serializable plan. `applyMapStage(plan, { sendCommand, readLogs,
signal, timeoutMs })` applies that plan after its matching Vanilla test server is
running. The application connects these helpers to `map stage`; the helpers do
not start a server or a client themselves.

Sponge `.schem` v1–3 and Java structure `.nbt` imports use a fresh world with a
void flat overworld generated by the exact target Vanilla server. Apply the returned
`serverProperties` to `server.properties` **before the first server start**.
Then call `applyMapStage`, using server-console commands and its log reader.
The importer waits for all requested chunks to load, compresses equal blocks
into bounded rectangular `fill` commands, restores property-bearing states
after their neighbors exist, and merges typed block-entity NBT afterward.
Numbers, arrays, long integers and Unicode strings retain their NBT types.
Large block-entity payloads and literal control characters use binary command
storage in the isolated world, followed by `data modify ... set from storage`;
they never become multiline console commands.
For Windows Java 17, the managed server explicitly selects UTF-8 console input.

Schematic offsets and negative coordinates are preserved. Java structure
coordinates begin at `(0, 0, 0)`; omitted structure cells and `structure_void`
are not placed. Explicit air is placed. A plan exposes `origin`, `bounds` and
`focus` for positioning the observer. Bounds can reduce an import; its default
hard budgets are 262,144 cells, 256 horizontal chunks and 20,000 commands.
The importer supports the three Vanilla dimensions and enforces their build
heights. Custom dimensions need a complete world with its dimension data pack.

A standalone `.mca` plan exposes `copiedWorldPath`. Supply that directory as
the managed server's world source before starting. The region and referenced
external `.mcc` chunk files are copied byte-for-byte; the game generates fresh
level metadata and neighboring chunks. The void preset controls the overworld;
the Nether and End retain normal Vanilla terrain in omitted cells and outside
the imported blocks. Legacy dimension folders and the
26.x `dimensions/minecraft/.../region` layout are selected for the target
version. Region compression 1, 2, 3 and Java LZ4 block streams (4) are readable;
LZ4 lengths, output bounds and masked XXH32 checksums are validated.

Every original input and sidecar is hashed before and after preparation and
application. A changed source fails verification. A unique storage marker is
read back from the **server log** after every 64 commands and at completion;
queued commands alone do not count as success. Parse and loading errors fail
the import. Cancellation interrupts preparation, copying, polling and command
batches; the caller stops its isolated server on failure or cancellation.
Preparation failures remove only the fresh, resolved UUID staging directory;
existing work folders and original input files remain untouched.

Free entities from Sponge v1–3 `Entities` and Java structure `entities` are
also imported, including armor stands, frames, mobs, paintings, displays and
nested passengers. Java `pos`/`blockPos` and Sponge `Offset` define placement;
saved absolute entity positions, hanging anchors and leash block positions
are translated with them. Rotation and rich typed NBT are retained. Root
anchors are culled against inclusive block bounds; passengers of retained
roots stay with their mount graph. Duplicate source UUIDs fail early.

Each plan remaps entity UUIDs and matching references to stable fresh UUIDs.
Retries remove only entities carrying that plan's unique tag, preserve and
temporarily disable drop gamerules, then wait for actual old UUID removal
before resummoning. Entity payloads come from binary command storage, so
literal newlines and other controls survive. The final native command checks
entity presence; queued summon commands alone are insufficient. A region-file
stage also copies its matching sibling saved-entity region and sidecars when
present. Original source files remain read-only.

The target server applies normal neighbor updates and block-entity ticking.
Dynamic or physically impossible source states can change and require a live
observation. Modded states and entity types require their corresponding modded
environment; an exact Vanilla server reports unsupported types as import
errors rather than silently dropping them.

Reader APIs expose entity and block-entity NBT for inspection. Saved Anvil
biome palettes and sky/block light nibble arrays are returned when present;
missing sections, missing arrays and portable files report unknown values.
The browser uses inspectable entity proxies; exact entity rendering remains
available through the native game framebuffer.

`tests/staging.test.ts` covers all three schematic variants, sparse Java
structures, offsets, typed entity payloads, source hashes, copied external
chunks, acknowledgement, rejected commands, cancellation and LZ4 corruption.
The LZ4 decoder was additionally checked against a real `lz4-java` 1.8.0
100,000-byte multi-block output, whose framing is defined by
[LZ4BlockInputStream](https://github.com/lz4/lz4-java/blob/master/src/java/net/jpountz/lz4/LZ4BlockInputStream.java).
Sponge v1's `TileEntities` and v2/v3's `BlockEntities` follow the
[Sponge format specification](https://github.com/SpongePowered/Schematic-Specification).
